Isolation: app replicas cannot reach auth, PostgreSQL, limiter, or Redis directly. PostgreSQL and Redis are not host-published; only Traefik exposes port 8080.

02 / Policy choices

Three algorithms, configured by route

Policies are defined server-side in app/policies.py. New accounts receive the basic tier; an operator may assign premium in PostgreSQL.

POST /v1/fixed

Fixed window

Basic5 / 60 sec
Premium10 / 60 sec

A counter expires 60 seconds after its first request.

POST /v1/sliding

Sliding-window log

Basic5 / rolling 60 sec
Premium10 / rolling 60 sec

Stores one timestamp per allowed request for an exact rolling limit.

POST /v1/token

Token bucket

Basic5 capacity; 5/min refill
Premium10 capacity; 10/min refill

Allows a burst up to capacity, then refills continuously.

Choosing an algorithm: fixed window is simple and compact but can burst at a reset boundary. Sliding log is precise but costs memory per request. Token bucket supports controlled bursts with a steady refill rate.

03 / State and atomicity

One key per user, route, and algorithm

The limiter hashes the verified subject before using it in Redis. Every limiter instance shares the same state; each script performs its read, decision, and write atomically.

verified subject + route + algorithm > rate-limit:v1:{algorithm}:{route}:{sha256(subject)}

Fixed window script

INCR the counter, set PEXPIRE on its first hit, compare with limit, and return the remaining TTL for retry guidance.

Sliding log script

Use Redis time, prune sorted-set entries outside the window, count live requests, then deny or add a unique timestamped request.

Token bucket script

Read tokens and last update time, refill up to capacity, consume one token when available, and persist the new state with expiry.

The Lua strings live in app/redis_store.py and are passed to Redis with EVAL. The store returns an allow decision, remaining count, and retry delay in milliseconds.

04 / Operator guide

Start it and exercise the request path

Run these commands from rate-limit/. Configure local secrets first; Compose starts PostgreSQL, auth, Redis, the limiter, Traefik, and app replicas. The interactive console is at http://localhost:8080/demo.

Start the stack

cp .env.example .env
# Set AUTH_JWT_SECRET and AUTH_DB_PASSWORD to random values.
docker compose up --build --scale app=3

Create an account and call a protected route

curl -i http://localhost:8080/v1/fixed \
  -H "Authorization: Bearer $ACCESS_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"message":"hello"}'

Run automated tests

docker compose --profile test run --build --rm auth-tests
docker compose --profile test run --build --rm tests
What to expect

For a basic account on /v1/fixed, five quick requests should pass and the sixth should return 429. Sign up at /auth/signup; never send a user ID in business JSON.

05 / Reliability and security

Trust starts at the gateway

Client identity is never trusted

ForwardAuth validates JWT issuer, audience, signature, expiry, and active account. Auth response headers overwrite caller-supplied identity and tier headers.

Authorization is data-backed

Roles and permissions are stored in PostgreSQL. Public registration always assigns the basic user role; promote administrators with the operator command.

Dependencies fail closed

Auth or PostgreSQL failure rejects protected requests; Redis failure returns 503. No backend outage bypasses checks.

Sliding logs trade memory for precision

One sorted-set member is kept per allowed request during the window. A high-volume service may choose an approximate sliding counter instead.

Use deployment-managed secrets

Local Compose reads JWT and database secrets from an ignored .env. Production should use a managed secret store, TLS, secured service discovery, and highly available databases.
