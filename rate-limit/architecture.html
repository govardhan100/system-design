04 / Decision returns: Redis replies to the limiter with allow/deny and remaining quota. The limiter returns 2xx to continue or 429 to reject; Redis errors fail closed with 503.
05a / ALLOW

Traefik forwards the original request to one FastAPI replica. The app handles business logic and returns its response through the gateway.

05b / DENY

Traefik returns 429 Too Many Requests with Retry-After. No app replica receives the request.

Network boundary: limiter connects to both edge and private Redis networks. Redis is private; app replicas and Traefik do not join the Redis network.

02 / Policy choices

Three algorithms, configured by route

Policies are defined server-side in app/policies.py. Basic is the default tier; only the configured demo identity receives premium limits.

POST /v1/fixed

Fixed window

Basic5 / 60 sec
Premium10 / 60 sec

A counter expires 60 seconds after its first request.

POST /v1/sliding

Sliding-window log

Basic5 / rolling 60 sec
Premium10 / rolling 60 sec

Stores one timestamp per allowed request for an exact rolling limit.

POST /v1/token

Token bucket

Basic5 capacity; 5/min refill
Premium10 capacity; 10/min refill

Allows a burst up to capacity, then refills continuously.

Choosing an algorithm: fixed window is simple and compact but can burst at a reset boundary. Sliding log is precise but costs memory per request. Token bucket supports controlled bursts with a steady refill rate.

03 / State and atomicity

One key per user, route, and algorithm

The limiter hashes the user ID before using it in Redis. Every app and limiter instance can share the same Redis-backed state; the script itself performs the read, decision, and write without a race between those steps.

user_id + route + algorithm > rate-limit:v1:{algorithm}:{route}:{sha256(user_id)}

Fixed window script

INCR the counter, set PEXPIRE on its first hit, compare with limit, and return the remaining TTL for retry guidance.

Sliding log script

Use Redis time, prune sorted-set entries outside the window, count live requests, then deny or add a unique timestamped request.

Token bucket script

Read tokens and last update time, refill up to capacity, consume one token when available, and persist the new state with expiry.

The Lua strings live in app/redis_store.py and are passed to Redis with EVAL. The store returns an allow decision, remaining count, and retry delay in milliseconds.

04 / Operator guide

Start it and exercise the request path

Run these commands from the project directory. Docker Compose starts Traefik, Redis, the limiter, and three application replicas.

Start the stack

docker compose up --build --scale app=3

Send a request through the gateway

curl -i http://localhost:8080/v1/fixed \
  -H 'Content-Type: application/json' \
  -d '{"user_id":"manual-test-user","message":"hello"}'

Run automated tests

docker compose --profile test run --build --rm tests
What to expect

For a new basic user on /v1/fixed, five quick requests should pass and the sixth should return 429 with Retry-After. Try /v1/sliding and /v1/token to exercise the other algorithms. Use a different user ID for a fresh quota.

05 / Reliability and security

What this demo assumes

Payload IDs need trusted identity

This demo reads user_id from JSON but does not authenticate it. In production, verify the caller and bind this ID to the authenticated principal.

Backend failure is fail-closed

If Redis cannot be reached, protected requests get 503 rather than bypassing the quota. Readiness checks Redis; liveness does not.

Sliding logs trade memory for precision

One sorted-set member is kept per allowed request during the window. A high-volume service may choose an approximate sliding counter instead.

Local Docker wiring is not production hardening

Compose uses the Docker socket for Traefik discovery and one Redis instance. Production needs secured discovery and Redis availability, capacity, and access controls.
