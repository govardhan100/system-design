1. Why Can't We Run BI Directly on PostgreSQL?

The Dual-Database Mandate

In high-scale e-commerce, running executive BI reporting or aggregations directly on the operational relational database is a catastrophic antipattern. Here is what happens when a query like SELECT category, SUM(quantity), AVG(price) FROM orders JOIN order_items ... GROUP BY category hits the production PostgreSQL cluster during peak traffic:

💥 Transaction Starvation & Lock Churn

PostgreSQL creates MVCC read snapshots that hold shared locks across table relations. Long-running analytical scans block autovacuum, exhaust available worker processes, and prevent live customer checkout transactions from completing.

🛑 Buffer Pool Cache Thrashing

A sequential scan across millions of order rows pulls gigabytes of historical data into PostgreSQL's shared_buffers, ejecting frequently accessed indexes and hot product cache pages needed for active storefront browsing.

The Fundamental Architectural Principle
OLTP is optimized for high-concurrency, short point writes and single-row lookups (Write-Heavy, O(log N) B-Tree lookups). OLAP is optimized for scanning hundreds of millions of values across a small set of columns (Read-Heavy, SIMD vectorized scans).

2. Storage Engine Mechanics: Row-Store vs Column-Store

Disk Layout & I/O Efficiency

The physical disk layout determines the fundamental performance envelope. Let's inspect how the same order row is laid out on disk:

Dimension PostgreSQL (OLTP Row-Oriented) ClickHouse (OLAP Column-Oriented)
Disk Layout All column attributes of a row are stored contiguously on 8KB disk pages. Each column is stored in its own dedicated, compressed file (e.g. category.bin).
Aggregation Query Must read the entire 8KB page into RAM even if only 1 column (e.g., total_amount) is needed. Reads strictly the queried column files. Zero bytes read for unused columns (notes, customer address).
Compression Ratio 1.5x – 2x (rows have heterogeneous data types mixed together, defeating compression algorithms). 5x – 15x (homogenous data types compressed with specialized algorithms: DoubleDelta, Gorilla, ZSTD).
Primary Index B-Tree Index: Pointer for every individual row (high memory overhead: 10GB+ index for 100M rows). Sparse Index: 1 index mark per granule (8,192 rows). Entire index fits comfortably in CPU L3 cache (a few megabytes).
CPU Vectorization Row-at-a-time iterator model (Volcano iterator: virtual function call per row). Vectorized SIMD execution: processes 64 to 256 array values in a single CPU cycle.

📐 I/O Bandwidth Mathematical Comparison

Suppose an e-commerce table contains $N = 10,000,000$ order records, where each complete row is $250 \text{ bytes}$, and a BI query aggregates total_amount ($8 \text{ bytes}$):

PostgreSQL I/O Scanned: Data = N_rows × Row_Size = 10,000,000 × 250 bytes = 2,500,000,000 bytes ≈ 2.50 GB (Disk / Buffer Pool) ClickHouse I/O Scanned (with 4x Compression): Data = (N_rows × Column_Size) ÷ Compression_Ratio = (10,000,000 × 8 bytes) ÷ 4 = 20,000,000 bytes ≈ 20 MB Result: ClickHouse reduces disk & memory I/O by 99.2% (125x less I/O)!

3. The ETL / ELT Pipeline: Moving & Transforming Data

Incremental High-Water Mark Architecture

How does live operational transactional data get moved into ClickHouse safely and reliably?

1. High-Water Mark Extraction

The pipeline maintains a persistent sync_checkpoint table in PostgreSQL recording last_synced_order_id. On each sync tick, it executes:

SELECT o.id, oi.id, c.name, p.category ... FROM orders o JOIN customers c ON o.customer_id = c.id JOIN order_items oi ON o.id = oi.order_id JOIN products p ON oi.product_id = p.id WHERE o.id > :last_synced_order_id ORDER BY o.id ASC LIMIT :batch_size;

2. Wide-Denormalization & Derived Metrics

OLAP databases hate runtime table joins. The pipeline flattens the 3NF schema into a wide event fact and computes derived business metrics in flight:

  • Financial Profit: profit = line_total - (cost_price * qty)
  • Partition Date: Formatted YYYY-MM-DD for partition pruning.
  • Low-Cardinality Encoding: Categoricals (category, country, status) mapped to ClickHouse dictionary keys.
Idempotency via ReplacingMergeTree
What happens if an order status is updated from PENDING to PAID? In standard databases, updates in append-only logs cause duplicates. ClickHouse solves this using the ReplacingMergeTree(synced_at) engine. During background part merges, rows sharing the same primary key (category, order_date, customer_id, order_id, item_id) automatically collapse to retain only the latest version based on synced_at.

4. Failure Scenarios & Resilience Hardening

Production Architecture Hardening

⚠️ The "Too Many Parts" ClickHouse Anti-Pattern

ClickHouse writes an immutable physical "part" (folder with column files) for every single INSERT statement. Inserting 1 row at a time causes ClickHouse to crash with:

DB::Exception: Too many parts (300). Merges are processing significantly slower than inserts.

Solution:

Always buffer writes in the pipeline into micro-batches of at least 1,000 to 100,000 rows, or utilize ClickHouse's asynchronous insert buffer (async_insert=1).

⚡ Transaction Boundary & CDC Drift

In high-throughput environments with concurrent long transactions, sequential IDs can commit out of order: Order #102 may commit before Order #101 finishes its write.

Solution:

In production enterprise architectures, replace polling with Change Data Capture (CDC) reading PostgreSQL's Write-Ahead Log (WAL) via Debezium and Apache Kafka. This guarantees exact transaction-commit order with zero polling overhead on the OLTP database.
