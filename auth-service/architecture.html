02 / Authentication

How identity is established

Authentication has two entry paths: credentials establish a session at signup or login; a bearer access token proves that identity again on each protected request.

Signup and login

Both public routes return an access JWT and a refresh token after credentials are accepted.

  1. Validate and normalize emailEmail must be valid; it is stripped and lowercased. Password length is 12 to 128 characters.
  2. Find or create the accountSignup rejects duplicate email; login loads the matching account and requires is_active=true.
  3. Verify or hash the passwordPasswords are checked or stored with Argon2id. Login failures use the same 401 response for unknown email and wrong password.
  4. Choose authorization defaultsSignup assigns the database user role and basic tier. Request-body role and tier values are ignored.
  5. Issue the token pairReturn a 15-minute access JWT and a random 14-day refresh token; store only the refresh token's SHA-256 hash in PostgreSQL.

Protected request via ForwardAuth

Traefik calls /verify before forwarding each protected /v1/* request.

  1. Extract bearer credentialMissing or malformed Authorization: Bearer … is rejected with 401.
  2. Verify the signed JWTPyJWT pins HS256 and requires valid signature, issuer, audience, expiry, issue time, token ID, subject, and typ=access.
  3. Reload current account stateThe token subject must match an active PostgreSQL user. Roles and permissions are loaded from SQL, not copied from the token.
  4. Return trusted identity/verify returns 204 and subject, roles, and rate tier headers. Traefik overwrites incoming client headers.
  5. Continue policy checksThe limiter uses verified subject plus stored tier; only an allowed request reaches an app replica.

Failure behavior: invalid or inactive credentials return 401. If PostgreSQL/auth cannot verify the request, ForwardAuth returns a non-success response and Traefik does not forward the protected request.

03 / Authorization

How permissions are enforced

Authentication answers “who is calling?” Authorization compares that account's current database permissions with the requirement on a route.

Permission check for GET /auth/admin/users

current_user validates the bearer token and loads the user's roles and permissions. require_permission("users:read") collects permission names across those roles. Missing permission returns 403; a match allows the handler to list users.

Current route scope: protected /v1/* routes require a valid active-user token and then apply the account's rate-limit tier; they do not currently require a named role permission. The admin user-list route is the implemented permission-gated example. No client-supplied role, permission, subject, or tier is trusted.

05 / Token lifecycle

Short-lived access, rotating refresh

Access JWT

15-minute lifetime; HS256 with configured issuer and audience, subject, issue/expiry times, token ID, and access-token type.

Refresh token

Opaque, 14-day lifetime. Only its SHA-256 hash is stored; each use revokes the presented token and issues a replacement.

Authorization

The seeded user role grants profile:read; operator-granted admin includes users:read.
