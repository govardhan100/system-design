Google ID Token & OpenID Connect Architecture

End-to-end cryptographic identity protocol from Browser to Google to Localhost Application

1. The Four-Stage Sequence Architecture

The OpenID Connect (OIDC) identity protocol solves authentication by issuing a cryptographically signed JSON Web Token (JWT) directly to the browser, which is then submitted to your backend application for signature verification and identity extraction.

1

Developer / Browser Request

The client loads Google Identity Services (GIS SDK). When the user clicks "Sign in with Google", a secure popup or redirect opens to Google's authentication servers with the application's client_id.

2

Google Authentication & Signing

Google verifies the user's password, 2FA, and user consent. Google then constructs the identity payload (sub, email, name, picture, aud, iss) and signs it using Google's private RSA key corresponding to a rotating key ID (kid).

3

Google ID Token Issuance

Google returns the signed ID Token (a 3-segment string: header.payload.signature) to the browser via the JavaScript credential callback.

4

Your Application (localhost) Verification

The browser posts the token to /api/auth/google-login. Your backend downloads Google's public JSON Web Key Set (JWKS) from https://www.googleapis.com/oauth2/v3/certs, verifies the RS256 signature, enforces that aud == CLIENT_ID and iss == accounts.google.com, and returns the verified user identity.

2. JWT Anatomy & Claims Breakdown

+-------------------------------------------------------------------------+
| HEADER: Algorithm & Key ID                                              |
| {"alg": "RS256", "kid": "8f3b21...", "typ": "JWT"}                     |
+-------------------------------------------------------------------------+
| PAYLOAD: User Identity & Security Claims                                |
| {                                                                       |
|   "iss": "https://accounts.google.com",                                 |
|   "sub": "109876543210987654321",                                       |
|   "aud": "123456789-xyz.apps.googleusercontent.com",                    |
|   "email": "developer.alex@gmail.com",                                  |
|   "email_verified": true,                                               |
|   "name": "Alex Morgan",                                                |
|   "picture": "https://lh3.googleusercontent.com/...",                  |
|   "iat": 1730000000,                                                    |
|   "exp": 1730003600                                                     |
| }                                                                       |
+-------------------------------------------------------------------------+
| SIGNATURE: RS256 Cryptographic Signature                                |
| RSASHA256(base64Url(header) + "." + base64Url(payload), GooglePrivKey)  |
+-------------------------------------------------------------------------+
Security Check Rule Vulnerability Mitigated
Signature Must verify against Google's active JWKS cert Token tampering & identity forgery
Audience (aud) Must strictly equal your GOOGLE_CLIENT_ID Token substitution attacks from another application
Issuer (iss) Must be accounts.google.com or https://accounts.google.com Rogue token authority spoofing
Expiration (exp) Must be greater than current Unix timestamp Replay of expired sessions
Subject (sub) Store as primary foreign key in your user database Email change confusion (emails can change; sub never does)

3. ID Token vs. Access Token

A frequent point of confusion in system design is the difference between an OAuth 2.0 Access Token and an OpenID Connect ID Token:

  • ID Token: An artifact of authentication ("Who are you?"). It is meant specifically for Your Application to consume and contains identity claims about the authenticated user.
  • Access Token: An artifact of authorization ("What are you allowed to access?"). It is meant for Google APIs (e.g., Google Drive, Calendar, YouTube) and is opaque to your client.
