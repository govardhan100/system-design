Database systems / connection lifecycle

PostgreSQL Connection Pool

A Dockerized FastAPI service borrows bounded PostgreSQL connections through psycopg_pool, returns each lease after use, and reports pool pressure.

01 / System architecture

One pool per API process. Shared database underneath.

The pool amortizes connection setup and caps the number of concurrent database sessions. The API runs synchronous psycopg calls in FastAPI's worker threadpool; the API and PostgreSQL share the backend, while local demo ports bind only to loopback.

02 / Operating boundaries

Bound concurrency. Observe reuse.

Pool size is per process

With multiple API replicas, total potential database connections are approximately replica count × max_size. Set limits with the PostgreSQL connection budget in mind.

Always use the connection context

with pool.connection() guarantees the lease returns on success or exception; never keep a connection globally checked out.

Pool stats are live signals

/pool/stats reports open/available connections and queued requests; the demo refreshes these while concurrent reads run.
